# 支付：决定、方案与待定问题（尚未实现）

## 1. 运营者的决定（2026-11-06）

- 收款用 **Stripe 在线支付**。
- 付款后由 **Mooring 定时从门户拉取付款记录**，自动开通或续期；不再由运营者手动设置。
- 计费同时支持**按月套餐**（"签约"）和**预付流量包**（pay as you go）。具体价格写在门户的配置文件里，不写进代码。

以下是运营者 2026-11-06 的决定，《使用约定》第 2 版按此写成：

- **只接受银行卡**，不接受支付宝和微信支付：两者的商户规则禁止 VPN 和代理服务（支付宝见 Stripe 的 `stripe.com/legal/alipay`，微信支付的规则同样禁止），付款记录也是实名的。约定第 1 条写「只接受银行卡」。
- **补偿与退款**：只有运营者一侧出故障才补偿：默认补时长或流量，用户坚持时才按停机时长退款。整个服务结束时，退还没用完的天数。退款原路退回银行卡；卡已经不能接收退款时，改补时长或流量。因违约被暂停、作废或封禁的，都不退款（约定第 6 条）。
- **到期三个月**：到期满三个月仍没有续期的用户，在 Mooring 里作废，随后删除他的门户账号（`delete-account`）。
- **取消自动续费**：用户在门户上自助取消（Stripe 的客户门户，第 2 节第 6 步），或请运营者取消。
- **作废时删卡**：作废一个用户时，运营者在 Stripe 删除他保存的银行卡。
- **封禁不退款**：因违法使用被封禁的用户，预付但没用完的时长或流量不退（用户 2026-11-06 原话「不退」；约定第 3、6 条）。以后给封禁加上付款身份之前，约定第 4 条要先列出它，并经用户确认。

## 2. 推荐方案：Stripe Payment Links + Webhook

| 方案 | 门户要持有的密钥 | 门户要做的 | 新增依赖 |
|---|---|---|---|
| **A. Payment Links（推荐）** | 只有 Webhook 签名密钥（`whsec_…`），只能用来验证，不能花钱、退款或查询 | 把用户带到运营者在 Stripe 后台建好的付款链接；接收并验证 Webhook | `hmac`、`sha2`（RustCrypto，MIT/Apache） |
| B. Checkout Sessions API | Stripe 私钥（哪怕是受限密钥，也能创建收款） | 从门户主机调用 Stripe API | HTTPS 客户端与 TLS 栈（reqwest 一类） |

A 的权限最小：门户主机被攻破时，攻击者拿不到能动钱的密钥。B 能动态定价、设置过期，但这些试点用不上。

### A 的流程

1. 运营者在 Stripe 后台为每个套餐或流量包建一个 Payment Link（固定价格，不允许顾客改数量），把链接地址、链接编号（`plink_…`）、价格和币种写进门户配置。
2. 已绑定的用户在订阅页点"购买"：门户用表单 POST（带 CSRF 检查）建一个待付款订单（随机编号），然后显示一个页面，上面是指向 `https://buy.stripe.com/…?client_reference_id=<订单编号>` 的**普通链接**。用链接而不是表单重定向，是因为 CSP 的 `form-action 'self'` 会拦下跨站重定向的表单提交。
3. 用户在 Stripe 的页面用银行卡付款：Payment Link 只开银行卡这一种付款方式。
4. Stripe 把 `checkout.session.completed`（异步付款还有 `checkout.session.async_payment_succeeded` / `…_failed`）发到 `POST /stripe/webhook`。门户：
   - 验证 `Stripe-Signature`：对 `<时间戳>.<原始请求体>` 做 HMAC-SHA256，常数时间比较，接受任意一个 `v1` 签名（换密钥期间会有两个），时间戳超过 5 分钟即拒绝；
   - 验证通过后才解析请求体，只读需要的字段；
   - 按事件编号去重（Stripe 会重发）；
   - 用 `client_reference_id` 找到订单，并核对 `payment_link` 等于该订单套餐的链接编号、`amount_total` 和 `currency` 等于配置的价格、`payment_status` 为 `paid`，全部一致才记为已付款；不一致的记为"需要运营者核对"，不开通；
   - 只返回 2xx 或 4xx，不在响应里回显任何内容。
5. Mooring 定时拉取已付款订单（第 3 节），开通或续期；门户的订阅页随后续快照显示新的到期和配额。
6. 取消自动续费：运营者在 Stripe 后台开启无代码的客户门户（no-code customer portal），并在门户配置里允许取消订阅；门户只在订阅页放这条登录链接。用户用付款时填的邮箱和 Stripe 发来的一次性验证码登录，在那里取消。门户因此仍然不需要任何 Stripe 私钥。Stripe 按邮箱找客户：同一邮箱有多个客户时，选最近创建、有生效订阅的那个（Stripe 文档，2026-11-06 核对）。Stripe 支持用 `prefilled_email` 参数预填邮箱，门户不用它：邮箱会进地址栏和浏览历史。

门户不接触银行卡信息，卡号只在 Stripe 的页面上输入。约定第 4 条列出 Stripe 那边保存的：付款页上填的邮箱和持卡人姓名，卡的品牌、末四位、有效期和发卡国家，以及反欺诈检查收集的 IP 地址、位置和设备信息。门户的订单保存 Stripe 的付款编号（约定第 4 条也列出），用来对上退款和争议事件。

## 3. 门户到 Mooring 的拉取契约（草案）

- 接口：`GET /api/mooring/entitlements?after=<序号>`，请求头 `Authorization: Bearer <拉取令牌>`。令牌由运营者在门户主机上用命令生成，只显示一次，门户只存摘要，可轮换、可作废。拉取按来源限流，不写日志。
- 返回：带 `format`、`version`、`generated_at` 的 JSON。每条已付款订单一项，有单调递增的 `seq`、订单编号、Mooring 用户编号（下单时的绑定）、类型（`monthly` 或 `topup`）、套餐编号、天数、流量字节数、金额、币种、付款时间；还有下一次拉取用的 `after`。
- Mooring 按订单编号**只开通一次**，保存游标。
- **纵深防御（建议 Mooring 实现）**：既然由 Mooring 拉取，门户被攻破时，攻击者就能伪造"已付款"记录来延长服务。建议 Mooring 在开通前用一把只读的 Stripe 受限密钥核对 Checkout Session 确实已付款、金额相符。这把密钥只放在运营者的 Mac 上，不放门户。这样门户只是"提示"，不是付款的唯一凭证。

## 4. 两种计费的含义（需要运营者确认）

| | 按月套餐（签约） | 流量包（pay as you go） |
|---|---|---|
| 买到什么 | 若干天的服务，和该期的流量配额 | 若干 GB 额外流量，在若干天内有效 |
| Mooring 怎么开通 | 把到期日从"现有到期日与现在中较晚者"往后延，设置配额 | 增加一笔额度；Mooring 需要支持跨计费周期累计的额度 |
| Stripe 模式 | 见下面的问题 1 | 一次性付款 |

**问题 1：签约要不要自动续费？**（已定，2026-11-06：两种都提供，都只收银行卡。）

- **预付月套餐（推荐先做）**：每月买一次，没有自动扣款、取消和催缴，实现和对账都简单；用户可以提前续。
- **自动续费**：要处理续费成功（`invoice.paid`）、续费失败、取消（`customer.subscription.deleted`）和退款。用户在 Stripe 的客户门户自助取消，或请运营者取消（第 2 节第 6 步）。

**问题 2：退款怎么处理？**（已定，2026-11-06：运营者一侧停机 8 小时及以上，包括服务器被封锁，补时长或流量；用户坚持时才按停机时长退款。整个服务结束时退还没用完的天数；退款原路退回银行卡，卡已不能接收退款时改补时长或流量。因违约被暂停、作废或封禁的，不退款。）门户会记录 Stripe 的退款和争议事件（`charge.refunded`、`charge.dispute.created`），并在拉取接口里给出撤销记录。退款由运营者在 Stripe 后台操作，门户不持有能退款的密钥。

**删除账号**：《使用约定》第 4 条将写"订单随账号删除"。付款的正式记录在 Stripe，门户的订单只是给 Mooring 开通用的提示，所以删号后门户不需要保留订单。删号之前，运营者要先做三件事：在 Stripe 后台取消该用户的自动续费（门户的服务器取消不了，不取消，删号后用户还会被扣款），处理完补偿或退款，并等 Mooring 拉取完该账号已付款的订单。作废用户时，还要在 Stripe 删除他保存的银行卡。到期满三个月没有续期的用户，按同样的步骤作废、删号。`delete-account` 删号后会把账号的行从数据库文件和日志里抹掉（`docs/security.md` 第 8 节）。计划让 `delete-account` 在有生效中的自动续费，或有未被拉取的已付款订单时拒绝删除。删号后才到达的退款、争议事件对不上订单，记为"需要运营者核对"。
