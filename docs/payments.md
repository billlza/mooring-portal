# 支付：决定、做法与开通步骤

门户已经能接单、接收 Stripe 的付款通知、把该开通的订单交给 Mooring 来取（分支 `feature/payments`，2026-11-11）。它还没有接过真实的 Stripe 账户；开通前要做的步骤在第 3、6 节。Mooring 一侧来取清单、开通或续期的程序已经合入 Mooring（2026-11-11）；按到期和配额自动暂停、恢复用户的每晚任务已经合入 Mooring（PR #46，2026-11-12），还没有部署。

不给门户配套餐文件时，门户和以前一样：不卖任何东西，套餐页写"付款还没有开通"，下面这些地址都不存在。数据库里还有没了结的付款时，门户拒绝这样启动（第 2.9 节）。

## 1. 运营者的决定

- 收款用 **Stripe 在线支付**（2026-11-06）。
- 付款后由 **Mooring 定时从门户拉取付款记录**，自动开通或续期；不再由运营者手动设置（2026-11-06）。
- 计费同时支持**按月套餐**（预付一个月，和自动续费两种）和**预付流量包**。具体价格写在门户的配置文件里，不写进代码（2026-11-06）。
- 2026-11-11：开通并接入付款。
- **流量包只算本周期**（2026-11-12）：流量包的流量只算进 Mooring 开通它的那个计费周期，到这个周期结束为止；没用完的不带到下个周期。套餐文件和给 Mooring 的清单里照旧有 `days`，但对流量包不生效，所以页面上不写流量包的天数。配额用尽后买的流量包，够补上超出的部分时，Mooring 的每晚任务在下一次运行时恢复服务。《使用约定》第 2 版按此写。
- **全额退款收回**（2026-11-12）：已经开通的订单被全额退款时，Mooring 从门户记下退款的时刻起，收回这张订单给的、还没用到的时间和流量，已经用掉的不追回；部分退款不改变服务。订单页对这样的订单写明这一点。Mooring 一侧已经实现（PR #46，2026-11-12 合入），《使用约定》第 2 版写明。

以下是运营者 2026-11-06 的决定，《使用约定》第 2 版按此写成：

- **只接受银行卡**，不接受支付宝和微信支付：两者的商户规则禁止 VPN 和代理服务（支付宝见 Stripe 的 `stripe.com/legal/alipay`，微信支付的规则同样禁止），付款记录也是实名的。约定第 1 条写「只接受银行卡」。
- **补偿与退款**：只有运营者一侧出故障才补偿：默认补时长或流量，用户坚持时才按停机时长退款。整个服务结束时，退还没用完的天数。退款原路退回银行卡；卡已经不能接收退款时，改补时长或流量。因违约被暂停、作废或封禁的，都不退款（约定第 6 条）。
- **到期三个月**：到期满三个月仍没有续期的用户，在 Mooring 里作废，随后删除他的门户账号（`delete-account`）。
- **取消自动续费**：用户在门户上自助取消（Stripe 的客户门户），或请运营者取消。
- **作废时删卡**：作废一个用户时，运营者在 Stripe 删除他保存的银行卡。
- **封禁不退款**：因违法使用被封禁的用户，预付但没用完的时长或流量不退（用户 2026-11-06 原话「不退」；约定第 3、6 条）。
- **封禁认卡**（运营者 2026-11-07 决定；约定第 1、3、4 条）：被封禁的人换了邮箱或门户账号，也要尽量认出来。门户的封禁名单除了邮箱的摘要，还记下被封者付款用过的银行卡的 Stripe 指纹的摘要，留到解封为止。门户没有 Stripe 密钥，自己查不到这些指纹：由运营者在 Stripe 后台读出，交给 `ban` 或 `ban-cards` 命令。以后用这些卡付的款不开通，由运营者在 Stripe 后台退款；开了自动续费的，还要取消订阅、删除保存的卡。误封时 `unban` 连指纹一起删。指纹只认卡号，换一张卡就认不出。运营者另在 Mac 上保存封禁记录，拿它比对每个新用户；这份记录不在门户里。

## 2. 做法：Stripe 的 Payment Links 和 Webhook，Mooring 来拉

门户不经手付款，也不持有任何能动钱的密钥。它只持有 Webhook 的签名密钥（`whsec_…`），这把密钥只能用来验证"这条通知是 Stripe 发的"，不能收款、退款或查询。门户主机被攻破时，攻击者拿不到能动钱的东西；他能做的是伪造"已付款"，第 6 节写了 Mooring 一侧怎样防这一手。

### 2.1 一笔付款的经过

1. 运营者在 Stripe 后台为每个套餐建一个 Payment Link，把它的地址、编号、价格和内容写进套餐文件（第 3 节）。
2. 已绑定的用户在订阅页点"下单"。门户建一张待付款的订单（随机编号，20 个字符），转到订单页；订单页上是一个指向 `https://buy.stripe.com/…?client_reference_id=<订单编号>&locale=<zh 或 en>` 的普通链接。用链接而不是表单，是因为本站的内容安全策略（`form-action 'self'`）不许表单提交到别的站点。
3. 用户在 Stripe 的页面上用银行卡付款。卡号只在 Stripe 的页面上输入。
4. Stripe 把事件发到门户的 `POST /stripe/webhook`。门户先验证签名，再读事件，然后按下面的规则记账。
5. Mooring 定时来取（`GET /api/mooring/entitlements`，契约见 `docs/contract/entitlements-v1.md`），按订单开通或续期。订阅页上的到期时间和配额，要等 Mooring 下一次导出快照、运营者导入之后才变。

### 2.2 什么样的付款才开通

一张订单只有在下面每一条都成立时，才写进给 Mooring 的清单：

| 条件 | 不成立时 |
|---|---|
| 这次结账确实付了款（`payment_status` 是 `paid`） | 还在等的（`unpaid`）不理会，Stripe 到账后会再通知；其余的进入"需要运营者核对" |
| 付款是在这张订单的套餐的那个 Payment Link 上做的 | 需要运营者核对 |
| 结账的种类对得上：自动续费的套餐是订阅，其余是一次性付款 | 需要运营者核对 |
| 金额和币种与下单时套餐的价格完全相同 | 需要运营者核对 |
| 订单保存的套餐内容和价格，现在的套餐文件里仍然有一模一样的一项 | 需要运营者核对 |
| 付款用的是直接输入的银行卡，而且这张卡不在封禁名单上 | 钱包（Apple Pay、Google Pay、Link）或其他方式付的、卡在封禁名单上的，都进入"需要运营者核对" |
| 账号这时仍然绑定着下单时的那个 Mooring 用户 | 需要运营者核对 |
| 这笔付款没有在开通之前被全额退款或被持卡人提出争议 | 不开通 |

订单保存的是下单那一刻套餐的内容和价格。套餐文件改了之后，旧的待付款订单不能再付（订单页会这样说），用户重新下单即可。留着旧的付款地址、在套餐改了之后还是付了款的，这张订单要运营者核对，不会不经人看就按旧的内容开通。付款通知到达时已经通过核对的订单，按它自己保存的内容开通，以后再改套餐文件不影响它。

"需要运营者核对"的订单，门户不猜、不自动开通，也不自动退款。运营者看过之后有两条路：在 Stripe 后台全额退款（门户收到退款通知后，这张订单就不再等人了），或者用 `approve-order` 放行。用户在订单页上只看到"需要运营者核对，请联系运营者"，看不到原因：原因里有一条是"卡在封禁名单上"。

放行只免掉 `orders` 给这张订单列出的那一条原因，其余的照常核对：

- 因为结账对不上而等着的（没付款、链接不对、种类不对、金额不对、套餐改过）：放行后回到"已付款"，接着按卡核对。卡通过了才写进清单；用钱包付的，会因为卡再等运营者一次；卡在封禁名单上的不开通。`orders` 在放行之前就写明这张订单的卡是哪一种情况，放行之后命令也会说订单现在停在哪里。
- 因为卡无法核对而等着的（钱包等）：放行就是"这张卡我看过了"，订单写进清单。
- 卡在封禁名单上的：不能放行，只能在 Stripe 全额退款。误封后解封也不改这个结论：封禁期间用这些卡付的款已经记成"卡在封禁名单上"，退款后请用户重新付款。
- 账号已经不绑定订单上那个 Mooring 用户的：先重新绑定，再放行。
- 已付款、但 Stripe 一直没有说这笔付款用的是什么卡的（"正在核对"）：也可以放行，这等于不核对卡。先在 Stripe 后台重发那条通知；重发不了（第 6 节）再走这一步。
- 已经全额退款或被争议的、已经在清单里的、还没付款的：拒绝，什么也不改。

### 2.3 事件的先后

Stripe 不保证事件的先后，也可能重发。门户的做法是：

- 每个事件按它的编号只记一次，重发的直接答 2xx。
- 结账完成的通知一到，就对到订单上（订单是在用户去付款之前建的，所以一定先存在）。
- 其余的通知都按 Stripe 自己的编号存成"事实"：某笔付款的卡核对结果、退了多少、有没有争议；某张账单是哪笔付款付的；某个订阅现在的状态。存下来的只有核对结果，没有卡的指纹。
- 每记一个事件，就在同一个事务里把这些事实和订单对一遍，该开通的写进清单。所以卡的通知先到还是结账的通知先到，结果一样（有测试，把各种顺序都试了一遍）。事务失败时什么也不记，Stripe 重发时再来。

### 2.4 自动续费

- 自动续费的套餐在 Stripe 那边是一个订阅。第一次付款对到用户下的订单上；之后每续一次，Stripe 发来一张账单已付的通知，门户据此生成一张"续费订单"（没有人下单，订单页会注明），内容和第一张相同，照同样的条件核对后写进清单。续费金额和第一张订单的价格不同时，进入"需要运营者核对"。
- 订阅的第一次付款和每次续费，Stripe 都是通过账单收的：门户要靠"这张账单是哪笔付款付的"这条通知（`invoice_payment.paid`）才能找到付款用的卡。这个事件没订上，自动续费的订单会一直停在"正在核对"。
- 续费的通知比开始这个订阅的结账通知先到时（Stripe 不保证先后），门户先把它记成"不属于任何订单的付款"；结账通知一到，它就转成续费订单，付款时间仍是 Stripe 当时说的那个（有测试，各种先后都试过）。
- 用户有一个还会续费的订阅时，订阅页显示它，并给出 Stripe 客户门户的登录链接，用户在那里取消。取消通常是"本期结束后不再续"，订阅页会相应地改口；订阅彻底结束后，这一栏消失，用户可以重新订。
- 一个账号有订阅还没结束时，不能再订自动续费的套餐。

### 2.5 退款和争议

退款由运营者在 Stripe 后台操作。门户收到通知后：已经开通的订单，在清单里追加一条退款记录，写明这笔付款累计退了多少、是不是已经全额退款（是不是全额以 Stripe 的说法为准：放行过的订单，实付金额可能和套餐价格不同，光看数字分不出来）；持卡人向银行提出争议时，追加一条争议记录。Mooring 怎样处理这两种记录由 Mooring 决定（契约第 4 节）。还没开通就全额退款或被争议的订单，不会再开通。开通前就被争议的订单会一直列在 `orders` 的待办里（写明"这里没有要做的事，去 Stripe 应对争议"），直到这笔付款在 Stripe 被全额退款，或账号被删除：门户不跟踪争议的结果。已经写进清单的订单不会被收回：之后才到的"卡在封禁名单上"之类的通知不再改它，只有退款和争议会在它后面追加记录。

### 2.6 不属于任何订单的付款

有人直接打开 Payment Link 付款而没有下单、对同一张订单付了两次、或者一个门户不认识的订阅续了费，这些钱都到了 Stripe，但对不上订单。门户把它们单独列出来等运营者处理：在 Stripe 全额退款后它自己从名单上消失，或者用 `dismiss-payment` 拿掉。

### 2.7 门户保存什么

- 订单：编号、账号、下单时绑定的 Mooring 用户、套餐的内容和价格、下单和付款的时间、状态、Stripe 的结账、付款、账单、订阅编号（《使用约定》第 4 条列出）。
- 对每笔付款：卡的核对结果（通过、在封禁名单上、无法核对）、累计退款、争议金额。
- 封禁名单上的卡：指纹的 BLAKE2s 摘要，不存指纹本身。
- 不保存：付款人的姓名、邮箱、地址，卡号、卡的品牌、末四位、有效期，IP 地址。Stripe 的事件里带着这些，门户读事件的代码根本不解析它们（有测试）。它们都在 Stripe 那边，约定第 4 条写了。
- 数据库装的是哪一种模式的付款（测试或正式，第 2.9 节）。
- 账号删除或封禁时，它的订单、清单里的记录和 Stripe 说过的关于这些付款的事实一起删除。Stripe 的事件编号保留 45 天后删除；从没对上任何订单的事实也在 45 天后删除。

### 2.8 删除账号

`delete-account` 在下面两种情况下拒绝，并说明原因：

- 账号有一个 Stripe 还可能扣款的订阅。门户取消不了订阅，删了账号用户还会被扣款。先在 Stripe 取消，等 Stripe 通知门户订阅已经结束。
- 账号有没了结的订单：已付款但 Mooring 还没取走的；或者在等运营者核对、既没有全额退款也没有被争议的。

`ban` 不等这些：它立即删除账号，并列出还要在 Stripe 取消的订阅。`unbind` 也不等，但会提醒：这个账号的订阅还在扣款，却已经没有 Mooring 用户可以开通了。

### 2.9 一个数据库只装一种模式的付款

Stripe 的测试模式和正式模式是两套互不相通的账。给 Mooring 的每一份清单只带一个 `livemode`，Mooring 据此决定开不开通；同一本清单里混着两种付款，演练的记录就会被当成真的开通。所以：

- 门户带着套餐文件启动时，数据库记下套餐文件的模式。此后模式不同的通知一律拒绝，什么也不记：答 400 并记一条错误日志，Stripe 后台会显示这次投递失败。
- 清单里的 `livemode` 取自数据库，不取自门户这一次启动用的套餐文件。
- 数据库里已经有订单或"不属于任何订单的付款"时不能换模式：门户拒绝用另一种模式的套餐文件启动，并说明该怎么办。演练完了，用 `discard-test-payments` 删掉演练留下的全部订单、付款和 Stripe 说过的事实（账号、绑定、封禁名单、拉取令牌都留着，清单的编号接着往下排，不重用），再换成正式的套餐文件启动。装过真钱付款的数据库不能这样清，也不能拿来演练：演练另用一个数据库。
- 数据库里还有 Stripe 可能再扣款的订阅、或没了结的订单时，门户拒绝**不带**套餐文件启动：那样 Stripe 的通知没有人收，Mooring 也取不到该开通的订单。要停售，先在 Stripe 停用 Payment Link、取消全部订阅，等 `orders` 里没有待办、Mooring 也取完了，再去掉这两个参数。去掉之后，Stripe 再发来的退款和争议门户收不到，Mooring 也就不会知道，要在 Stripe 后台看。

## 3. 开通步骤

这些都要运营者本人做：门户不持有 Stripe 的任何密钥，也不能替人开账户。

1. **Stripe 账户**：注册并完成验证。Stripe 是否接受这类业务、英国的消费者权益和增值税、出口线路的运营商条款是否允许收费，都要运营者自己判断，代码回答不了。
2. **只留银行卡**：在 Stripe 后台的付款方式设置里，只开银行卡，关掉 Apple Pay、Google Pay 和 Link。钱包不能按 Payment Link 单独关（2026-11-11 查 Stripe 文档）。没关的话，用钱包付的款都会进入"需要运营者核对"：钱包付款带来的指纹可能是设备令牌的，不是卡号的，封禁认卡就不准了。
3. **为每个套餐建一个 Payment Link**：
   - 固定价格，不允许顾客改数量，不开优惠码。
   - 自动续费的套餐用订阅价格，计费周期设成"每 N 天"，N 就是套餐文件里的 `days`。按自然月扣款的话，31 天的月份会有一天接不上。
   - 付款完成后跳回 `https://<门户域名>/subscription`。
   - 记下链接地址（`https://buy.stripe.com/…`）和链接编号（`plink_…`）。
4. **客户门户**（有自动续费的套餐时）：开启无代码的客户门户，允许取消订阅，不允许换套餐和改数量。记下登录链接（`https://billing.stripe.com/p/login/…`）。
5. **Webhook 端点**：地址 `https://<门户域名>/stripe/webhook`；API 版本选 `2026-10-28.endive`（端点的版本在创建时定下，以后不变；同一个 `endive` 发布下更新的版本也可以）；订阅这些事件：

   ```
   checkout.session.completed
   checkout.session.async_payment_succeeded
   charge.succeeded
   charge.refunded
   charge.dispute.created
   invoice.paid
   invoice_payment.paid
   customer.subscription.updated
   customer.subscription.deleted
   ```

   多订了别的事件没有关系，门户收下后不理会。把端点的签名密钥（`whsec_…`）写进门户主机上的一个文件，一行，权限 0600。
6. **套餐文件**（不含任何密钥，格式见第 4 节）。只能让它的属主改写（权限 0644 或更严）：同组或其他用户可写时门户拒绝启动。谁能改这个文件，谁就能把付款引到别人的 Payment Link 上。
7. **启动门户**时加上两个参数：

   ```bash
   mooring-portal --db <数据库> serve --origin https://<门户域名> --behind-proxy --payments <套餐文件> --stripe-webhook-secret <密钥文件>
   ```

   两个参数必须一起给。文件有问题时门户拒绝启动并说明原因，不会把密钥的内容打印出来。密钥文件超过 4096 字节时整份拒绝，不会只读前一半。改了套餐文件或密钥文件要重启。
8. **给 Mooring 一把拉取令牌**：`mooring-portal --db <数据库> pull-token`。令牌只显示这一次，门户只存它的摘要。
9. **先用测试模式走一遍**：Stripe 的测试模式有自己的 Payment Link、端点和签名密钥。套餐文件里写 `"livemode": false`，页面上会注明"现在是测试模式"，清单里也带着 `livemode: false`，Mooring 不应该据此开通（契约第 5 节）。走通之后：停下门户，运行 `discard-test-payments` 清掉演练的记录，换成正式模式的链接、端点、密钥，`"livemode": true`，再启动（第 2.9 节）。两种模式的链接不要混写：门户不检查链接属于哪种模式。写错时，这种付款的通知要么根本发不到门户（那种模式没有建端点），要么因为签名密钥或模式对不上被拒绝；钱已经在 Stripe 收下而订单不动，要运营者去 Stripe 退款。
10. **让 Stripe 也拦住被封的卡**（建议）：门户的封禁名单只是不开通，钱还是会被收下，要运营者去退。把同样的卡指纹加进 Stripe Radar 的拦截名单，这些卡在 Stripe 那里就付不成。

反向代理要把 `/stripe/webhook` 和 `/api/mooring/entitlements` 原样转给门户：不改请求体（签名是对原始字节算的），不记录 `Authorization` 请求头。门户主机的时钟要准：签名时间和本机时钟相差超过 5 分钟的通知会被拒绝。

## 4. 套餐文件

```json
{
  "format": "mooring-portal-payments",
  "version": 1,
  "livemode": false,
  "currency": "gbp",
  "plans": [
    {
      "id": "month-100",
      "kind": "month",
      "days": 30,
      "traffic_gb": 100,
      "amount": 800,
      "payment_link": "https://buy.stripe.com/…",
      "payment_link_id": "plink_…"
    }
  ],
  "manage_subscription_url": "https://billing.stripe.com/p/login/…"
}
```

每个键都必须出现，出现未列出的键即拒绝。样例：`contract/fixtures/payments/demo.json`。

| 键 | 含义 |
|---|---|
| `livemode` | 这些 Payment Link 收的是不是真钱。数据库记下这个模式，Stripe 发来的通知模式不同就拒绝（第 2.9 节） |
| `currency` | 全部套餐的币种，小写：`aud`、`cad`、`cny`、`eur`、`gbp`、`hkd`、`sgd`、`usd` 之一（都以"分"为最小单位） |
| `plans` | 1 到 24 个套餐，页面按这个顺序列出 |
| `id` | 套餐编号：1 到 32 个 `a-z`、`0-9`、`-`，不以 `-` 开头或结尾，不重复。订单和给 Mooring 的清单用它称呼套餐 |
| `kind` | `month`（一个月，付一次）、`month_auto`（一个月，Stripe 每期自动扣款）、`traffic`（流量包） |
| `days` | 1 到 3660。`month`、`month_auto`：买到的服务天数；`traffic`：也要写，但不生效：流量包只算进开通它的那个计费周期（第 1 节），页面也不显示它 |
| `traffic_gb` | 1 到 100000，十进制 GB。`month`、`month_auto`：这一期的流量配额；`traffic`：额外流量 |
| `amount` | 价格，以币种的"分"计，1 到 10000000，和 Stripe 里的金额一致 |
| `payment_link` | `https://buy.stripe.com/` 加上链接自己的那一段，不带参数。两个套餐不能共用一个链接 |
| `payment_link_id` | `plink_` 开头的链接编号。Stripe 在每笔付款里带回它，门户靠它确认钱是付在这个套餐的链接上的 |
| `manage_subscription_url` | 客户门户的登录链接，`https://billing.stripe.com/p/login/` 开头；没有 `month_auto` 套餐时可以写 `null` |

价格以 Stripe 为准：套餐文件里的 `amount` 写错了，付款金额对不上，订单会进入"需要运营者核对"，不会按错的价格开通。

## 5. 运营者命令

| 命令 | 作用 |
|---|---|
| `orders` | 列出：等运营者处理的订单和原因、等 Stripe 通知的订单、不属于任何订单的付款、Stripe 还可能扣款的订阅、对不上订单的退款和争议、最近 20 张订单、Mooring 取到了哪里。每一项都写明下一步怎么做 |
| `approve-order --order <订单编号>` | 放行一张订单，只免掉 `orders` 给它列出的那一条原因（第 2.2 节）：结账对不上的，接着按卡核对；卡无法核对或 Stripe 一直没说卡的，写进给 Mooring 的清单。命令会说订单现在停在哪里。卡在封禁名单上、已经全额退款、被争议、已在清单里、还没付款，或账号不再绑定订单上那个 Mooring 用户的，拒绝 |
| `dismiss-payment --id <序号>` | 把一笔不属于任何订单的付款从名单上拿掉。全额退款的会自己消失 |
| `pull-token` | 生成 Mooring 拉取用的令牌，替换以前的。只显示一次 |
| `revoke-pull-token` | 作废拉取令牌 |
| `discard-test-payments` | 演练之后、收真钱之前用：删掉测试模式留下的全部订单、不属于任何订单的付款和 Stripe 说过的事实，并抹除副本。账号、绑定、封禁名单、拉取令牌留着。装着真钱付款的数据库拒绝 |
| `ban --account <编号> --card <指纹> …` | 封禁，并记下这些卡。指纹在 Stripe 后台该笔付款的卡片详情里；`--card` 可以重复 |
| `ban-cards --email <地址> --card <指纹> …` | 给已经封禁的邮箱补记卡 |

换签名密钥：在 Stripe 后台轮换时，旧密钥还能用一段时间。把新旧两把密钥各占一行写进密钥文件，重启门户，两把签的通知都认；旧密钥过期后删掉它那一行，再重启。

## 6. 还没做的，和要知道的

- **Mooring 一侧的拉取程序还没有写。**在它写好之前，门户记下的"该开通"没有人取，付了款不会自动开通。契约在 `docs/contract/entitlements-v1.md`。门户被攻破时，攻击者能伪造"已付款"的记录来骗开通，所以契约建议 Mooring 开通前用一把只读的 Stripe 受限密钥核对付款确实存在、金额相符；这把密钥只放在运营者的 Mac 上。
- **没有接过真实的 Stripe 账户。**事件的格式是照 Stripe 的文档（2026-11-11 核对，API 发布 `endive`）和仓库里的合成样例（`contract/fixtures/stripe-events/`）实现的，签名校验用另一种语言算出的结果核对过。第一次接真实账户，必须先在测试模式里把一次性付款、自动续费、续费、取消、退款各走一遍。事件的 API 版本不是 `endive` 时，门户拒绝并记一条错误日志，Stripe 会重发并在后台显示失败，不会悄悄丢掉。
- 门户不处理付款失败、争议的结果、订阅暂停。这些都不会让门户多开通什么；续费扣款失败时 Stripe 自己会重试或结束订阅，结束时门户会收到通知。
- **丢了的通知。**门户没收下的通知，Stripe 在正式模式下自动重试三天（测试模式只在几小时内重试三次）。之后可以手动重发：在 Stripe 后台是事件产生后 15 天内，用 Stripe 的命令行工具是 30 天内（Stripe 文档，2026-11-11 核对）。过了这个期限还没收到的：订单会停在"正在核对"，用 `approve-order` 放行（等于不核对卡）；订阅结束的通知丢了，门户会一直以为 Stripe 还可能扣款，这个账号就删不掉，只能用 `ban` 删除后再 `unban`。`orders` 列出的待办要定期看，别等到过期。
- 停售之后（去掉 `--payments` 启动），以前的付款再发生退款或争议，门户收不到通知，清单里也就没有记录（第 2.9 节）。
- 收据、付款人的邮箱和取消续费时的验证码都由 Stripe 发，门户不发邮件。

## 7. 本地演练（不需要 Stripe 账户）

用仓库里的合成套餐文件和合成事件，可以在本机把整条路走一遍。签名密钥是随手编的，只在本机有效。

```bash
mkdir -p target/demo && chmod 700 target/demo
```

```bash
printf 'whsec_local_rehearsal_0123456789\n' > target/demo/whsec && chmod 600 target/demo/whsec
```

```bash
cargo run -p mooring-portal -- --db target/demo/portal.db serve --origin http://localhost:8080 --payments contract/fixtures/payments/demo.json --stripe-webhook-secret target/demo/whsec
```

按 README 的演示流程注册并绑定一个账号，然后在订阅页对"月付"点"下单"，记下订单页上的订单编号。下面的脚本把一个合成事件里的订单编号换成它，签名后发给门户（合成事件的说明见 `crates/core/tests/contract/payments.rs`）：

```bash
deliver() {
  body=$(sed "s/0123456789abcdefghjk/$ORDER/" "contract/fixtures/stripe-events/$1.json")
  at=$(date +%s)
  signature=$(printf '%s.%s' "$at" "$body" | openssl dgst -sha256 -hmac "$(cat target/demo/whsec)" -r | cut -d' ' -f1)
  curl -sS -o /dev/null -w "$1: %{http_code}\n" -X POST http://localhost:8080/stripe/webhook -H "Stripe-Signature: t=$at,v1=$signature" --data-binary "$body"
}
```

```bash
ORDER=<订单编号>; deliver checkout-payment; deliver charge-payment
```

两条都答 `200` 后，刷新订单页，状态是"已付款，等待开通"。合成事件里的时间是写死的（北京时间 2026-11-11 08:01），所以订单页上的付款时间会早于下单时间；真实的事件没有这个问题。再生成拉取令牌，模拟 Mooring 来取：

```bash
cargo run -p mooring-portal -- --db target/demo/portal.db pull-token
```

```bash
curl -sS -H "Authorization: Bearer <令牌>" "http://localhost:8080/api/mooring/entitlements?after=0"
```

`deliver charge-refunded-part` 之后再取，会多出一条退款记录。自动续费的套餐对应的事件是 `checkout-subscription`、`invoice-paid-first`、`invoice-payment-first`、`charge-first-invoice`，续费是 `invoice-paid-cycle`、`invoice-payment-cycle`、`charge-cycle-invoice`。`orders` 命令随时显示门户这边的账。

门户说套餐文件"同组或其他用户可写"而拒绝启动时，是这份检出的文件权限比 0644 宽（umask 是 002 时会这样）：`chmod go-w contract/fixtures/payments/demo.json`。演练完了停下门户，清掉演练的记录：

```bash
cargo run -p mooring-portal -- --db target/demo/portal.db discard-test-payments
```
