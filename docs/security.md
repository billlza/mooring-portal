# 安全设计与威胁模型

门户属于安全等级 Level 2（用户认证）：保护的是门户账号、会话、已绑定用户的订阅数据（状态、用量、配额、到期），以及运营者上传的每个用户的 CFM 配置（含节点凭据和地址）和订阅链接。

## 1. 威胁模型

| 攻击者 | 能力 | 门户的应对 |
|---|---|---|
| 互联网上的任何人 | 注册、猜密码、批量请求、伪造跨站表单、诱导用户点击 | 限流；Argon2id；登录失败不泄露账号是否存在；CSRF 三重检查；安全响应头；除首页外不运行脚本，首页只运行本站自己的脚本文件（第 6 节） |
| 已注册的普通用户 | 用自己的会话访问任意地址 | 页面、下载和链接管理只依据会话里的账号取数，地址和表单里没有账号或用户编号可改；越权测试覆盖 |
| 拿到某个用户订阅链接的人 | 拉取这个链接 | 只能取得这一个用户的配置，直到用户重新生成、停用链接或修改密码；见第 9 节 |
| 拿到数据库副本的人（如备份外泄） | 读取整个 SQLite 文件 | 密码只存 Argon2id 摘要，会话令牌和订阅链接令牌只存 BLAKE2s 摘要，副本里没有能直接用的会话或链接。**但 CFM 配置是明文**：门户必须把它原样交给 CFM。副本外泄等于全部已绑定用户的节点凭据外泄（第 9 节、第 11 节）。删除过的账号在副本里找不到，除非副本做于删除之前（第 8 节）；被封禁的地址只留 Argon2id 摘要，拿候选地址可以试出来（第 10 节） |
| 同一主机上的其他本地用户 | 读文件 | 数据库文件以 0600 创建，权限过宽时拒绝启动 |
| 网络上的观察者 | 看到流量 | 部署时必须由反向代理终止 TLS；Cookie 全部 `Secure`，并发送 HSTS |
| 能改动下载页所跟随的发布信息的人（控制了 CFM 的 GitHub 仓库，或在主机取数据的途中） | 让主机取到假的或被改过的发布描述 | 途中的由 TLS 挡住；描述逐项校验，页面上的地址由版本号和写死的仓库地址拼出，不从描述里抄，所以链接不到别处。控制了仓库的人挡不住：他发布什么，下载页就推荐什么（`docs/releases.md` 第 3 节，本文第 11 节） |

不在范围内：主机本身被攻破、运营者操作失误、浏览器或操作系统被攻破。主机被攻破虽然防不住，但它的后果因为保存了 CFM 配置而变大了，第 9 节写了应对。

## 2. 账号与密码

- 登录名是邮箱，规范化为小写 ASCII，校验从严（ASCII、恰好一个 `@`、dot-atom 本地部分、带点的主机名）。v1 不发邮件，不验证邮箱，邮箱只是用户记得住的登录名。
- 密码策略参照 NIST SP 800-63B 和 OWASP ASVS：12–128 个字符（按 Unicode 字符计），不设组合规则，不得等于邮箱或其 `@` 前部分，不得含控制字符；原样哈希，不裁剪。
- 哈希：Argon2id，19 MiB、2 轮、1 条并行（OWASP 推荐配置），PHC 字符串自带盐和参数，日后调高成本时旧哈希仍可校验。
- 同时最多 2 个哈希在跑（每个约占 19 MiB）。要哈希的请求先领号，最多 18 个请求同时持号（2 个在算、16 个排队；按推荐成本，登录排队不到一秒，注册要算两次哈希，最多约一秒）；号领完时立即答"服务器正忙"（503），不读库，也不计入该邮箱的校验次数。洪水请求因此只占有界的内存和等待时间，队列不会无限变长。
- 登录时邮箱不存在，就对一个预先算好的诱饵哈希做一次校验，耗时与密码错误相同；错误提示统一为"邮箱或密码不正确"。
- 注册时先哈希密码、再算邮箱的封禁摘要，然后才查重，"邮箱已注册""被封禁"与成功注册耗时相近（有测试：三种情况都在受限的线程池里算两次）。但注册表单本身必然会告诉提交者这个邮箱已被注册（开放注册又不验证邮箱时无法避免），只能靠限流减缓批量探测。邮箱验证要等外部 SMTP 凭据，见 README "待定事项"。
- 账号编号：60 位随机数，写作 Crockford base32 `xxxx-xxxx-xxxx`，只在账号主人登录后可见。运营者**只按编号绑定，不按邮箱绑定**：开放注册证明不了谁拥有某个邮箱，按邮箱绑定会让抢先用别人邮箱注册的人拿到别人的订阅信息。

## 3. 会话

- 令牌是操作系统随机源产生的 256 位随机数，以 `__Host-session` Cookie 交给浏览器：`Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/`、无 `Domain`，有效期 30 天。
- 数据库只存令牌的 BLAKE2s-256 摘要。防的是数据库副本外泄后被直接冒用会话。令牌有 256 位熵，摘要无法反推。
- 每个账号最多保留 10 个会话，旧的先清；每建一个新会话时顺手清掉所有已过期会话。表的大小有上限，不需要后台任务。
- 退出登录删除当前会话；修改密码删除该账号所有会话，只给当前浏览器发一个新的；运营者删除账号时连同会话一起删除。
- 令牌缺失、格式不对、未知或过期，一律视为未登录。

## 4. CSRF

所有改变状态的请求（登录、注册、退出、改密码、切换语言、生成和停用订阅链接）都是表单 POST，必须同时满足：

1. 若浏览器发了 `Sec-Fetch-Site`，它必须是 `same-origin` 或 `none`；
2. 若浏览器发了 `Origin`，它必须等于配置的 `--origin`；
3. 请求体是 `application/x-www-form-urlencoded`，其中的 `csrf` 字段与 `__Host-csrf` Cookie（`SameSite=Strict`）中的令牌一致（常数时间比较）。

`__Host-` 前缀使子域名或明文 HTTP 响应都无法种下或改写这个 Cookie，因此双提交成立。登录和退出时轮换 CSRF 令牌。

`Cookie` 头按字节切分。父域名或本机其他应用的 Cookie 可能含非 ASCII 字节，浏览器会把它和本站的 Cookie 放在同一个头里；按字节切分后，它不会连带本站的会话和 CSRF Cookie 一起失效（否则用户会显示为未登录，所有表单都返回 403）。

Referrer 策略用 `same-origin` 而不是 `no-referrer`：在 `no-referrer` 下，浏览器给本站自己的表单 POST 发送的是 `Origin: null`（Fetch 标准"append a request Origin header"），会被第 2 条拒绝。这是本机浏览器实测发现的，已用测试固定。站外链接仍不带 referrer。

语言切换和登录后跳转只接受预先命名的页面（枚举），不接受地址，从结构上杜绝开放重定向。

## 5. 限流

| 限制 | 键 | 额度 |
|---|---|---|
| 登录尝试 | 客户端网络（IPv4 单址，IPv6 按 /48） | 15 分钟 20 次 |
| 密码校验（登录或改密码） | 邮箱，无论账号是否存在 | 15 分钟 10 次，校验成功即清零，所以实际限制的是失败次数 |
| 注册尝试 | 客户端网络 | 1 小时 10 次 |
| 订阅链接拉取 | 客户端网络，无论链接是否存在，在读令牌之前计数 | 1 小时 600 次 |
| 订阅链接拉取 | 每条有效链接 | 1 小时 60 次 |
| 账号总数 | 全站 | `--max-accounts`，默认 200 |

- 每次密码校验在哈希之前、在限流器的锁内计数，校验成功后再清零。若先查额度、哈希完再记失败，并发请求会在任何一次失败记上之前全部通过检查：30 个同时到达的猜测会真的校验 30 次，而不是 10 次（有并发测试）。
- IPv6 按 /48 而不是 /64 计：隧道服务商免费给出整个 /48（65,536 个 /64），按 /64 计时一个人就能用新键塞满限流器。代价是共用一个 /48 的用户（例如同一移动运营商的邻居）共用额度；用户只有几个人，这种情况很少，额度也足够。
- 每个限流器最多跟踪 1 万个键。满了先丢弃已关闭的窗口，仍满就拒绝（返回"稍后再试"）：被超大规模攻击时有界失败，不会无限占用内存。
- 客户端地址只在内存里用于限流，不写日志、不落库。
- 放在同机反向代理后面时用 `--behind-proxy`：只信任回环地址来的连接，取 `X-Forwarded-For` 的最后一项。缺这个头、或有非回环连接直接到达，都按配置错误报 500，不悄悄退回用代理自身的地址（那样所有用户会共享一个限额）。

## 6. 响应与页面

- `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`：除首页外，所有响应都是这一条，页面里没有脚本，也不允许脚本；不内联样式。有表单、账号数据或订阅链接的页面都在其中。
- **首页是唯一的例外**（2026-11-10）。运营者要求把界面做得更好看，并说可以用 three.js。实现时的选择是：只让首页运行脚本，用它把主图变成会动的场景；不引入 three.js，见本节末尾。成功返回的 `GET /`（和 `HEAD /`）的策略在上面那条之后多两项：`script-src 'self'; worker-src 'none'`。策略由响应头中间件按请求的方法、路径和响应的状态决定，页面的处理函数改不了它（`crates/web/src/security/headers.rs`）；首页出错时返回的错误页不在例外之内。
  - 允许的只是本站自己的脚本文件。内联脚本、`onclick` 之类的属性、别处的脚本仍然被拒绝。`default-src 'none'` 还在，`connect-src` 回落到它，所以脚本不能自己发起连接（`fetch`、XHR、WebSocket 都不行）；`worker-src 'none'` 让它启动不了 Worker。页面本来能做的事它仍然能做：加载本站的图片、提交本站的表单、让浏览器跳转到别的地址，后果见下面"要说清楚的代价"。
  - 脚本是 5 个 ES 模块，共约 33 KB，编进二进制，按内容哈希放在同一个目录下（`/assets/js.<哈希>/`）。它只做一件事：在首页主图上用 WebGL 2 画场景。有测试检查它的源码里没有 `fetch`、`eval`、`innerHTML`、`document.cookie`、`localStorage`、`location` 等用法，也没有写成 `http://`、`https://` 或以 `//` 开头的外部地址。
  - 这个例外不给外人可乘之机，靠的是三条不变量，每条都有测试：
    1. 只有成功返回的首页允许脚本，其余每一种响应（页面、错误页、重定向、`/sub/`、配置下载、资源，以及首页自己出错时的错误页）的策略逐字不变；
    2. 首页不显示请求带来的任何东西。带着恶意的查询串、Cookie 和请求头去取首页，得到的页面一个字节都不变。页面里唯一来自请求的是 CSRF 令牌，而它只接受 64 位十六进制；
    3. 请求能影响内容的响应，没有一种是脚本类型。只有那 5 个模块以 `text/javascript` 返回，它们的内容是固定的。模块脚本必须是脚本类型才会运行，`nosniff` 对普通脚本也是同样的要求。查询串不合法时，现在返回本站自己的错误页，不再由框架把请求内容原样写回。
  - **要说清楚的代价**：以前的保证是"任何页面都不运行脚本"。现在是"只有首页运行本站自己的文件"。脚本一旦在首页运行，它就有本站的全部权限：能读页面里的 CSRF 令牌，能打开账户页和订阅页并读取其中的内容，包括替已登录的用户生成订阅链接并读走，还能带着这些跳转到别处；它读不到 `HttpOnly` 的会话 Cookie，不知道当前密码就改不了密码。所以上面三条不变量和脚本本身的内容，现在是要守住的东西。
  - 页面不依赖这段脚本：主图本来就在，脚本只是在它上面画。浏览器没有 WebGL 2、用户在系统里选了"减少动态效果"、场景画得太慢（平均低于每秒 24 帧，先降两次分辨率，仍慢就停）、显卡上下文丢失时，显示的都是原来的静态主图。场景运行时页面左下角有一个暂停按钮；暂停之后，窗口大小变化、显卡上下文恢复或"减少动态效果"关掉时，画面仍然是暂停的那一帧，按钮也还在。场景没有出现时，主图所在元素（`.hero`）的 `data-scene` 属性写着原因：`reduced-motion`、`no-webgl2`、`no-layers`、`layers-barred`、`too-slow`、`refused` 或 `context-lost`；出现时是 `live`。
  - 场景里的陆地和星轨圆环就是主图里的那两部分（同一段绘制代码另外输出的两个图层），天空、水面和灯光由着色器画：着色器里的颜色都是主图用过的（有测试，测试读不懂的颜色写法算失败）；银河的位置、星星的大小和灯光的范围在着色器里照着主图另写了一遍，有测试在其中一处被单独改动时失败。此外场景还有主图没有的东西：星空绕极点缓慢转动、星星闪烁、偶尔的流星、灯光摇曳、水面的波纹与反光，以及随鼠标轻微滑动的天空。主图里的星星位置是固定的，场景里的是另算的，所以场景淡入时星星会换位置。
  - 没有引入 three.js：它最新的满 14 天的版本（0.186.1）只发布未压缩的构建，画这个场景要用到的两个文件共 2.1 MB；而场景需要的着色器无论如何都要自己写，three.js 能替掉的只有约 140 行的绘制代码。
  - 只在 Chromium（本机的应用内浏览器）里实际运行过：场景出现、控制台无报错、暂停与继续、显卡上下文丢失与恢复、暂停之后上下文丢失再恢复、模拟手机宽度时的场景；审查时另用 Chrome 157 的无头模式运行过修正之前的那一版。Safari、Firefox、手机上真实的显卡、30 Hz 的屏幕都没有实际运行过；其余情况（没有 WebGL 2、减少动态效果、太慢、图层加载失败等）由不依赖浏览器的测试覆盖。
- 另有 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: same-origin`、`Strict-Transport-Security: max-age=31536000`、`Cross-Origin-Opener-Policy` 与 `Cross-Origin-Resource-Policy: same-origin`、`Permissions-Policy`。
- 页面 `Cache-Control: no-store`；样式、图标、主图及其两个图层、脚本模块按内容哈希命名，缓存一年。
- 不从任何外部主机加载资源，只用系统字体，没有统计、验证码或 CDN。
- 所有输出经模板自动转义；错误页由固定文本构成，生成过程不会失败。
- `robots.txt` 禁止收录，页面带 `noindex`。这是为少数受邀用户提供的服务，默认不求被搜索到；是否公开收录由运营者决定。
- 不启用响应压缩：页面里有 CSRF 令牌，压缩会引入 BREACH 类侧信道。

## 7. 日志

只记录运行事件：启动、停止（含收到的信号）、注册成功（不写是哪个账号）、被拒的伪造或格式错误请求（原因）、服务器错误（错误链）。不记录密码、令牌、Cookie、邮箱、账号编号或客户端地址：日志比被删除的账号留得久，所以它不点名任何账号（《使用约定》第 2 版第 4 条把这一点列为门户开放的前提）。错误链只在数据库的内容已经损坏或前后不一致时，才引用存储的值（例如两个 Mooring 用户编号）；`Email` 的 `Debug` 输出是打码的，令牌和密码类型的 `Debug` 输出是 `<redacted>`。

运营者命令的输出里有账号编号和 Mooring 用户编号：在终端里手动运行，不要让 cron、systemd 或邮件把它存下来，那些记录比删号留得久。

订阅链接的令牌在请求路径里，而门户不记录任何请求的路径；拉取本身也不记录日志。CFM 配置的 `Debug` 输出只有字节数。

被拒请求的原因在类型上就是固定文本（`&'static str`），请求里带来的任何内容都写不进日志。表单解码器的错误信息会引用字段的原值，所以被丢弃。有测试截获整个流程（注册、改密码、退出、登录失败与成功、格式错误和伪造的表单）的日志，确认其中没有密码、邮箱、账号编号、会话和 CSRF 令牌，也没有请求自己选的值；另一个测试截获生成、拉取、停用链接和下载配置的日志，确认其中没有链接令牌和配置内容。

## 8. 数据与文件

- 一个 SQLite 文件（WAL 模式），以 0600 创建；SQLite 新建的 `-wal`、`-shm` 文件沿用同样的权限（有测试确认）。权限过宽时拒绝打开。
- 只有 `serve` 会新建数据库。运营者命令要求文件已经存在：`--db` 写错时报错，不会对一个新的空库操作并报告成功。
- 服务与运营者命令可以同时打开这个文件，等待对方的锁最多 5 秒。迁移在写事务内读取版本号，两个进程同时打开一个新文件时只执行一次。唯一不等待的情形：两个进程同时把一个刚创建、尚未切换的新文件切换为 WAL 时，后到写入这一步的一方已持有读锁，SQLite 为避免死锁直接报 "database is locked"；这只可能发生在服务首次启动的那一刻，重试一次命令即可。
- 保存的内容：账号（编号、邮箱、密码摘要、时间）、会话摘要、绑定、已绑定用户的最新快照记录（状态，暂停时含原因和开始时间；本计费周期的用量、配额和到期时间）、已绑定用户的 CFM 配置（明文）与配置包的生成时间、订阅链接（令牌摘要与生成时间）、封禁名单（被封账号邮箱的摘要与封禁时间，第 10 节），以及下载页提供的 CFM 发布（版本、发布时间、磁盘映像的 SHA-256、上次核对的时间；都是公开信息，`docs/releases.md`）。
- **删除后不留副本**：每个连接都开着 SQLite 的 `secure_delete`，删除的行在它所在的页和释放出的页里写成零。这还不够：SQLite 在调整树的时候会重建页面，重建后的页留着搬走的单元原来的字节，以后删掉这一行，清零的只是它现在所在的单元（审查在一段长而杂的历史里找到过整行被删的账号，测试按同样的样子直接放进一份副本）；写前日志（`-wal`）也留着改过的每一页之前的版本，而服务运行时日志一直都在。所以凡是删除或改写数据的运营者命令（`unbind`、`import`、`import-profiles`、`delete-account`、`ban`、`unban`），做完后都先抹除，再写报告：用 `VACUUM` 按现存的行重建整个数据库，再把整个日志抄进数据库文件并截断为零（`wal_checkpoint(TRUNCATE)`）。重建时的临时副本只放在内存里（`temp_store`）。先抹除再写报告，输出出错（例如管道已关）也跳不过抹除。其他连接正在读写时最多等 5 秒；等不到就先写完报告再报错，命令做的事已经生效，用 `erase-deleted` 补做。旧版本建的数据库里以前删掉的内容，第一次抹除时也一并清掉。有测试：服务开着连接时删号、封号、解绑、导入把用户列为作废的配置包、导入更新的快照、解封之后，数据库文件和日志里都找不到被删的内容（邮箱、编号、Mooring 用户、配置里的凭据、令牌摘要、换下的用量、封禁摘要），而留下的都还在；输出出错时也是这样；放进页面空闲处的副本被抹掉。服务自己做的删除和改写（退出登录、过期和超出数量的会话、停用或重新生成链接、修改密码时换下的密码摘要）大多当场清零，剩下的副本在下一次运营者命令抹除时清掉。
- 备份里含密码摘要、邮箱和全部 CFM 配置，应按同样的权限保管，并当作节点凭据对待。删号和封禁抹不到已经做好的备份。

## 9. CFM 配置与订阅链接

配置只经运营者的 `import-profiles` 进入门户（契约见 `docs/contract/cfm-profiles-v2.md`）。配置包只含运营者点名的已绑定用户，没有门户账号的用户，凭据不经过门户主机。门户只检查外形，原样保存，原样交出：登录后的下载按会话取该账号自己的配置，订阅链接按令牌取该链接所属账号的配置。

- **令牌**：操作系统随机源产生的 256 位随机数，写作 64 个十六进制字符，链接是 `<origin>/sub/<令牌>`。数据库只存 BLAKE2s-256 摘要，同一令牌不可能属于两个账号（唯一约束）。
- **只显示一次**：令牌只出现在生成它的那个页面上（`Cache-Control: no-store`）。之后订阅页只显示生成时间，门户自己也无法再找回令牌；忘了就重新生成。
- **失效**：重新生成会让旧链接立即失效；用户可以停用；**修改密码会停用链接**（拿到会话的人可能生成过链接，账号主人改密码后它必须失效，有测试）；解绑或删除账号时链接随绑定删除（外键级联）；配置包把用户列入 `withheld` 时，原因是作废（`revoked`），链接随配置一起永久停用，之后再交付也不恢复；原因是暂停或没确认当前版本的使用约定，链接只暂停，拉取答 404，再交付后照常可用（都有测试）。暂停不降低安全性：暂停期间凭据不变，恢复后链接取到的还是同一个用户的配置。需要切断的情形，例如设备被查、凭据外泄、违法使用，走作废；用户自己也可以停用链接或修改密码，暂停期间同样可以。
- **漏列不停用**：配置包必须点名每一个已绑定账号的用户。漏了谁，多半是运营者列名单时的失误，不是停止服务的决定：整份配置包被拒绝，配置和链接都不变，错误里列出漏掉的账号（有测试）。
- **按写入时的会话行事**：会话在请求头到达时就读过了，而表单的请求体可以晚很久才到。生成和停用链接因此在写入的那个立即事务里重新按会话令牌找账号：会话在这期间结束了（退出、改密码、账号被删），就按未登录处理。否则，偷到会话的人可以在主人改密码之后仍拿到一条新链接；账号行号又会被复用，被删账号的请求甚至可能落到下一个注册的人身上（两种情形都有测试，请求体由测试控制，到点才放出）。
- **拉取**：不带也不种 Cookie（这个路由不在 CSRF 层里）；未知、格式不对、已停用的令牌，以及该账号没有配置，一律 404，不区分；`/sub/` 下的任何地址都由拉取处理，失败一律答纯文本：HTML 错误页会加载样式表并带链接，浏览器会把带令牌的地址作为 Referer 发出去，落进反向代理的访问日志。按网络计数在读令牌之前，按链接计数在找到有效链接之后：CFM 连接时经自己的隧道拉取，所有已连接用户都来自运营者出口的同一个地址，所以网络额度放宽，每条链接另有自己的额度，一个人反复「更新」挤不掉别人。不压缩（CFM 0.5.1 只接受 identity 编码）。
- **明文保存的理由**：门户必须把配置原样交给 CFM，能解密的密钥只能放在同一台主机上。加密存储挡不住主机被攻破，也不比 0600 的文件权限更能挡住本机其他用户，只多一份要管的密钥，不降低实际风险，所以不做。
- **门户主机被攻破或数据库外泄时**：在 Mooring 里为全部用户更换凭据，重新导出、导入配置包，并请用户在 CFM 里「更新」。

## 10. 封禁

封禁是运营者的单独操作：`mooring-portal --db <文件> ban --account <编号>`。它不从配置包推断：Mooring 的作废不带原因，自己不用了的用户也会被作废，这样的人应该能回来。

- **做什么**：在一个立即事务里删除该账号，连同会话、绑定、快照记录、CFM 配置和订阅链接，和 `delete-account` 一样，所以被封的人立即退出、不能再登录，链接永久停用；同时把该账号邮箱的摘要记进封禁名单，以后用这个邮箱注册会被拒绝（有测试，包括事务中途失败时什么也不改）。
- **怎样算同一个邮箱**：和注册时的规则完全相同，只去掉首尾空白、把整个地址转成小写。本地部分的点号和 `+` 后缀都保留，也不把不同的域名当成同一个（例如 `googlemail.com` 与 `gmail.com`）：这些规则只对部分邮箱服务成立，用在别处会把两个人当成一个人，误伤别人（有测试）。
- **存什么**：只存邮箱的 Argon2id 摘要和封禁时间，不存地址本身；被删的账号行也不留副本（第 8 节，有测试），所以外泄的数据库里没有被封者地址的原文。摘要故意算得慢：19 MiB 内存、两遍，和 OWASP 给密码的建议相同，每算一次几十毫秒。拿到数据库的人仍然可以拿候选地址去试，单个地址或一小批候选一试就知道。把已发放的纯数字 QQ 号（最长 10 位，不到 10^10 个）全部试一遍，按每次 30 毫秒算要几个核年：随手做不到，但租几百个核几天就能做完，用优化过的实现或 GPU 还更快；而且盐是公开的固定值，试一遍就同时认出名单上的每一个，任何一份副本都一样。要让外泄的数据库本身试不出来，得给摘要加一把不进数据库和备份的密钥，现在没有做（第 11 节）。参数和盐是固定的，不随密码的哈希设置变：服务器注册时和运营者命令封禁、解封时必须算出同一个摘要，参数一变，以前的封禁就全部失效，所以有测试钉住一个地址的摘要。注册时在同一个限量的哈希线程池里多算这一次，和密码哈希一样不阻塞服务。名单不随时间删除。
- **注册时怎么答**：被封的地址和已经注册过的地址得到完全相同的回答，状态码和那句话都一样。否则任何人输入一个地址，就能知道它的主人被封过（有测试）。
- **做不到的**：换一个邮箱就能重新注册。门户不做 IP 封禁、设备指纹，也不收集手机号；要做，先问运营者。付款上线后，封禁名单还要记下被封者付款用过的银行卡的 Stripe 指纹，以后用这些卡付的款不开通（运营者 2026-11-07 决定，做法见 `docs/payments.md` 第 1、2 节；《使用约定》第 2 版第 3、4 条写明）；指纹只认卡号，换一张卡就认不出。真正的关口是绑定这一步：只有运营者能把账号绑定到 Mooring 用户，也只有运营者能在 Mooring 里建用户，所以重新注册的人拿不到服务，除非运营者再为他绑定。运营者另在 Mac 上保存封禁记录，拿它比对每个新用户（不在门户里）。
- **还要在 Mooring 里作废**：门户不连接 Mooring。封禁一个绑定过的账号后，命令会提醒运营者在 Mooring 里作废那个用户；在那之前，节点照常为他的凭据服务。
- **误封**：`unban --email <地址>` 把地址从名单里删掉；付款上线后，还要连同这次封禁记下的卡指纹一起删。被删除的账号不会恢复，要重新注册、重新绑定。
- **不退款**：被封禁的人预付但没用完的时长或流量不退（运营者 2026-11-06 决定；《使用约定》第 2 版第 3 条写明）。

## 11. 已知的剩余风险

- 注册表单会暴露"某邮箱已注册"，只有限流能减缓（第 2 节）。被封禁的地址也是这样回答，所以它暴露的是"注册过或被封过"，不单独暴露封禁。
- 被封禁的人换一个邮箱就能注册新账号（第 10 节）；能挡住他的，是运营者比对封禁记录、不再为他绑定。付款上线后，用被封过的卡付的款也不开通，但换一张卡就认不出。
- 拿到数据库或备份的人能拿候选地址去试封禁名单：单个地址或一小批候选很快就能试出来；把纯数字 QQ 号全部试一遍要几个核年，租来的算力几天就能做完，一次就认出名单上的全部（第 10 节）。给摘要加一把不进数据库和备份的密钥能堵住，代价是多一份要单独保管的密钥：丢了它，所有封禁都失效。
- 没有邮箱验证，就没有自助找回密码：忘记密码只能请运营者删号后重新注册、重新绑定。
- 账号锁定（同一邮箱 15 分钟 10 次失败）可能被人故意触发，让真正的用户 15 分钟内无法登录。这是用限流防暴力猜测的通常代价。
- 掌握大量网络的攻击者（僵尸网络，或许多个 /48）能塞满某个限流器的 1 万个键，使新客户端在一个窗口内被拒（有界失败，见第 5 节）；也能以每个网络每小时 10 次的速度占满 `--max-accounts` 的注册名额。运营者可以用 `accounts` 找出未绑定的账号并删除。根本的办法是运营者发放邀请码或做邮箱验证，属于产品决定（见 README "待定事项"）。
- 门户是一个公开网站：它的域名、页面内容，以及用户从大陆访问它这件事本身，都会被网络观察到。未开代理时访问门户，用户所在网络能看到访问的域名。这改变了 Mooring "只用文件、不留链接"的低可见度做法，托管位置和域名需要运营者决定（见 README）。
- 慢速连接攻击（slowloris）要靠前置的反向代理处理，门户自身不设请求超时。
- 下载页跟随 GitHub 上 CFM 的最新正式发布，没有人为每个版本把关（运营者 2026-11-10 要求不能有人工步骤，`docs/releases.md`）。控制了 `billlza/cfw-rs` 仓库或其发布权限的人，能让门户向用户推荐他上传的文件；页面上的 SHA-256 与文件同出一源，发现不了这种替换。门户能保证的只是：下载地址一定在这个仓库的发布目录下。
- 首页运行本站自己的脚本（2026-11-10，第 6 节）。站点从"任何页面都不运行脚本"变成了"只有首页运行"，这道防线不再是绝对的：以后若有改动让首页显示了请求带来的内容，或让某个可被请求影响的响应以脚本类型返回，或脚本本身被改坏，后果是脚本以本站权限运行。现有测试守着这几条，但测试只能发现它们检查的那几种改法。
- 首页的场景只在 Chromium 里实际运行过（第 6 节）。在别的浏览器里出问题时，按设计应当退回静态主图；着色器在某些显卡上画错而不报错的情况，测试发现不了。
- 门户主机现在保存全部已绑定用户的节点凭据和地址：主机被攻破、数据库或备份外泄，影响的是全部用户的接入，而不只是显示用的数据（第 9 节写了应对）。这是采用订阅链接的代价，托管位置需要运营者权衡。
- 订阅链接泄露后，在用户重新生成、停用或修改密码之前一直有效。门户按设计不记录拉取，所以无法区分泄露者的拉取和用户自己的拉取。
- CFM 会把链接（含令牌）存在它的配置记录里，以便「更新」；用户的电脑被他人使用时，链接随之暴露。
- CFM 0.5.1 每次导入和「更新」都先用系统 DNS 解析门户的域名，以便连接之前确认对方是公网地址（`release/0.5.1` 的 `fetch.rs`，`SystemSubscriptionDnsResolver`）。在系统代理、本地代理和 TUN 加系统代理这几种模式下，它经自己的 SOCKS 端口拉取，但代理用 `socks5://` 而不是 `socks5h://`，域名在本机解析；纯 TUN 模式下它不经代理，这次连接由 TUN 接管。这次查询谁能看到，取决于 TUN 开没开（2026-11-07 读 `release/0.5.1` 的源码核对，没有抓包）：
  - 没开 TUN 时，系统 DNS 就是用户所在网络的 DNS，它能看到门户的域名。CFM 在系统代理模式下不改系统 DNS。
  - 开了 TUN（包括 TUN 加系统代理）时，CFM 的 macOS 隧道把自己设为所有域名的 DNS（`PacketTunnelProvider.swift`，`NEDNSSettings` 的 `matchDomains = [""]`），CFM 的内核拦下发往 53 端口的查询（`cfw-singbox-config/src/projection.rs` 的 `hijack-dns`），经所选线路用加密 DNS 解析，所在网络看不到。门户发的配置只有 `outbounds`，不带 DNS 策略，所以 CFM 用自己的加密 DNS。开了「中国大陆直连」时，在「规则」模式下只有 `geosite:cn` 名单里的域名改由境内的加密 DNS 直连解析（`mainland.rs`），名单外的照旧经节点。
  - 连接本身在「规则」和「全局」模式下经节点，SNI 在隧道里；「直连」模式下不经节点，SNI 能被看到。CFM 的内核没在运行时直连，DNS 和 SNI 都能看到。
- 删除只抹到数据库文件和它的日志（第 8 节）。删除之前做好的备份、主机商的快照、文件系统和磁盘一层（例如固态硬盘的磨损均衡）可能还留着旧数据，门户管不到；备份要定期轮换。用 `sqlite3` 之类的工具直接改库时没有开 `secure_delete`，删掉的行会留在空闲空间里，直到下一次门户命令抹除；删除只用门户自己的命令。
- 配置包只含运营者点名的用户（2026-11-06 决定只导出已绑定用户）。运营者点错了人，例如点了一个没有门户账号的用户，他的凭据仍会随配置包经过门户主机。门户不保存这份文档，导入时逐个报出这些用户并提醒立即删除配置包文件。用 `bound-users` 的输出点名就不会点错。
